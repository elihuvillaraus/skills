## 1. Preflight details: package manager, monorepo, git state, hooks

5. **Package manager detection** — Identify the package manager from lockfiles before running commands: `pnpm-lock.yaml` → `pnpm`, `yarn.lock` → `yarn`, `bun.lockb` or `bun.lock` → `bun`, otherwise `npm` when `package-lock.json` exists. Use that manager consistently for install, test, lint, typecheck, and dev-server commands. **Monorepo detection** — If the repo root contains a `pnpm-workspace.yaml`, `turbo.json`, `nx.json`, or a `packages/` / `apps/` directory structure, you are in a monorepo. Run install from the repo root (`pnpm install` / `yarn install`). Run test, lint, and typecheck commands from inside the relevant workspace package (e.g., `cd apps/web && pnpm test`) unless the root `package.json` exposes a scoped script (e.g., `pnpm --filter web test`). For dev server, start only the affected app package — do not start all apps.
5b. **Pre-start git status check** — Before writing any code, run `git status` to inspect the working tree. If there are uncommitted changes in files you do NOT own (from a previous interrupted session or another ralph instance), output `RALPH_BLOCKED: dirty working tree detected — uncommitted changes in <files> not owned by this story. Human review required before proceeding.` If the uncommitted changes ARE in your owned files (e.g., a previous partial attempt), stash or discard them (`git restore <files>`) and start fresh from the clean baseline. **Git hook awareness** — If the project uses pre-commit hooks (husky, lefthook, or similar — indicated by a `.husky/` or `.lefthook.yml` at the repo root), those hooks will run automatically during any `git commit` made by the documenter. Ensure your code passes lint and type checks before signaling, since hook failures will block the commit. Never use `--no-verify` to bypass pre-commit hooks.

## 2. Test isolation, flakiness, RTL, timeouts, coverage

**Test isolation rules:**
- Each test must be independent — no test should rely on state left by another test
- Use `beforeEach`/`afterEach` (or equivalent) for setup and teardown of mocks, DB state, or fixtures
- Use **test data factories or builder functions** for constructing test inputs and expected objects — a factory is a function like `createUser({ email: 'test@example.com' })` that returns a fully-populated object with sensible defaults so tests only specify the fields they care about. This avoids fragile inline literals scattered across tests and prevents all tests from breaking when a required field is added to the model.
- Mock external *third-party* services only (payment processors, email/SMS providers, other vendor APIs) — tests must not make real network requests to services you don't own
- **Never mock your own database or internal services.** This is the single most common way "TDD" produces tests that always pass while the feature never actually works: a mocked DB client cannot fail the way a real one does. RLS policies, missing column `DEFAULT`s, foreign keys, unique constraints, and triggers only reject a write when the write is real — mock the client and every one of those failure modes silently disappears from your tests. If a story creates, updates, or deletes data, **at least one test must run against a real test database** (this project's existing test-DB setup — a test schema, a transaction that rolls back, a seeded local DB, a test container) and then **read the value back** to confirm it actually landed, not just assert the function returned without throwing. A test that only checks "the mock was called with the right arguments" proves your code *called* the DB layer, never that the DB *accepted* the write.

**Flaky test guard:** If a test passes on first run but fails intermittently, it is a flaky test — not an acceptable state. Common causes: time-dependent assertions, non-deterministic ordering, shared global state. Fix root cause before signaling done. Do not use `--retry` flags to hide flakiness.

**React Testing Library (RTL) async patterns:** When testing components that update state asynchronously (data fetches, form submissions, timers), use RTL's async queries: `await findBy*` for elements that appear after an async operation, `waitFor(() => expect(...))` for assertions that require retries. Never use bare `getBy*` immediately after a user action that triggers async work — it will race and produce false failures. Wrap state-updating interactions in `act()` only when using low-level React APIs directly; RTL's `userEvent` and `fireEvent` wrap `act()` automatically.

**Test timeouts:** Integration tests that hit a real database or external service can be slow. If a test times out with the project's default timeout (typically 5000ms for Jest/Vitest), increase the timeout for that specific test using the test framework's per-test option (e.g., `{ timeout: 15000 }` in Vitest, or `jest.setTimeout(15000)` inside the test). Do not increase the global default — only raise it for the tests that genuinely need it. Never set a timeout so high it masks a hung test (cap at 30000ms for DB tests, 60000ms for tests involving file I/O or network calls).

**Coverage:** If the project has a coverage threshold configured (in `vitest.config`, `jest.config`, or similar), run `npm test -- --coverage` and verify the branch/line coverage does not drop below the project's threshold. Do not merge with a coverage regression.

## 3. General code rules (all stories)

- Match the types, function signatures, and import paths from the spec; use the project's existing path aliases (e.g., `@/lib/...`) consistently; use `import type` for type-only imports (keeps bundles clean and avoids circular dependency issues). For complex async or multi-step state (e.g., loading/error/success, idle/pending/fulfilled/rejected), model state as a **discriminated union** rather than multiple boolean flags — e.g., `type State = { status: 'idle' } | { status: 'loading' } | { status: 'success'; data: T } | { status: 'error'; error: Error }`. This makes impossible states unrepresentable and lets TypeScript narrow correctly in each branch.
- Follow existing patterns in the codebase (naming, error handling, exports)
- No magic strings or magic numbers — extract repeated literals into named constants or enums so intent is explicit (e.g., `const SESSION_EXPIRY_SECONDS = 86400` instead of `86400` inline)
- Always throw structured `Error` objects with descriptive messages (e.g., `throw new Error('User not found')`) — never throw raw strings or numbers; never swallow errors with empty `catch {}` blocks
- No `any` types in production code or test files; no `@ts-ignore` or `@ts-expect-error` comments (they bypass type checking — fix the type instead); no `// eslint-disable` or `/* eslint-disable */` inline suppression comments (they silence lint rules — fix the violation instead; the only permitted exception is a project-wide eslint config for a rule the team has explicitly decided to relax globally); no placeholder code; no TODOs. Prefer the `satisfies` keyword over `as` casts when you need to check an expression conforms to a type without widening it (e.g., `const config = { ... } satisfies Config` instead of `const config = { ... } as Config`); `as` discards excess property errors and is a type assertion, not a type check.
- No `console.log`, `console.debug`, `console.error`, `console.warn`, or any temporary debug statements — remove all before signaling. If the project has a structured logger (e.g., `pino`, `winston`, `@/lib/logger`) use it for intentional logging; do not introduce ad-hoc console statements as a substitute. When logging errors in request handlers or background jobs, always include structured context — at minimum `{ requestId, userId, path, error }` — so that incidents can be correlated across services. Never log raw Error objects without extracting `message` and `stack`; log the stack only at `error` level, not `warn` or `info`.
- No commented-out code — delete dead code entirely rather than commenting it out
- No unused imports — remove any import that is not referenced in the file. If the project uses a dead-export checker (e.g., `knip`, `ts-prune`, or an ESLint plugin), ensure no new unreferenced exports are introduced by your changes.
- Code comments: only add comments when the logic genuinely needs clarification; do not narrate obvious code

## 4. Story-type checklists (apply the ones your story touches)

- **If the story touches a database schema**: verify the change is backward-compatible (additive only — new nullable columns or new tables). If it's a breaking change, add a rollback migration alongside the forward migration and document both in the PR summary. **Migration verification** must include the exact apply command, rollback command when present, and evidence that generated SQL matches the intended schema change. When adding new columns that will be used in `WHERE`, `ORDER BY`, `JOIN ON`, or foreign-key lookups, add a database index on those columns in the same migration — a missing index causes full-table scans that degrade performance silently as data grows.
- **If the story performs multi-step database mutations**: wrap related writes in a single transaction so partial failures don't corrupt data. Also audit for N+1 query patterns — batch or join instead of looping queries. For list endpoints returning potentially large datasets, prefer cursor-based (keyset) pagination over offset pagination — cursor pagination is stable under concurrent inserts and performs better at scale. Consider **idempotency** for retries, duplicate form submissions, webhook replays, and background jobs; add uniqueness guards or safe no-op handling where the domain requires it. For concurrent edit scenarios (multiple users or processes updating the same record simultaneously), implement **optimistic concurrency control**: add a `version` integer or `updatedAt` timestamp column and include a `WHERE id = :id AND version = :expectedVersion` clause in UPDATE statements — if the row was modified since the client last read it, the update affects 0 rows; return a 409 Conflict so the client can reload and retry. For HTTP APIs where the resource is also served with ETags, include `If-Match` / `ETag` header handling as the HTTP-layer equivalent. For transient failures (network blips, DB connection timeouts), implement retry logic with exponential backoff — do not retry immediately in a tight loop. Cap retries at 3 attempts maximum. If the mutation writes data that is also cached (Next.js Route Cache, React Query, SWR, Redis, CDN), **invalidate or revalidate the relevant cache entries** after the write — stale cache returning old data after a mutation is a bug (e.g., call `revalidatePath`, `queryClient.invalidateQueries`, or delete the Redis key as appropriate).
- **If the story creates or modifies UI components**: for Next.js App Router projects, place `"use client"` at the top of any component that uses browser-only APIs, React hooks, or event handlers — Server Components cannot use these. Prefer Server Components by default; add `"use client"` only when necessary to minimize client-side bundle size. For React components, ensure every `useEffect` that sets up subscriptions, timers, or event listeners returns a cleanup function to prevent memory leaks. For effects that trigger async fetches, use `AbortController` to cancel in-flight requests on cleanup and guard against stale-closure race conditions (e.g., a slow request completing after a faster one) (e.g., `return () => subscription.unsubscribe()`). Verify keyboard navigation works (interactive elements reachable by Tab), semantic HTML is used (`<button>` not `<div onClick>`, `<label>` associated with inputs), focus order matches the visual flow, and controls/images expose **screen-reader accessible names** through text, labels, `aria-label`, or `alt` text. For UI that updates content dynamically without a page reload (e.g., status messages, loading indicators, error alerts, live data feeds), add `aria-live="polite"` (or `aria-live="assertive"` for critical alerts) to the container so screen readers announce changes — without it, dynamic updates are invisible to assistive technology. For Next.js App Router pages that include async Server Components or streamed segments, wrap the async parts in a `<Suspense fallback={<LoadingSkeleton />}>` boundary and provide a `loading.tsx` file in the route segment so Next.js streams a shell immediately — without a Suspense boundary the page blocks until all awaited data resolves. Also provide an `error.tsx` file in the route segment to catch render errors and display a graceful fallback instead of a blank crash — without `error.tsx`, unhandled errors in Server Components bubble up to the nearest parent error boundary or crash the full page. Capture **screenshot evidence** before and after visible changes, or explicitly state why the story has no visual surface. If the story implements **optimistic UI updates** (updating local state before the server confirms), trigger an optimistic rollback to the previous state on request failure — never leave the UI diverged from server state after an error. If the component can throw during render (e.g., async data loading, third-party widget), wrap it in or verify an **Error Boundary** exists in the parent tree so rendering errors surface a graceful fallback UI instead of a blank white screen.
- **If the story calls external APIs or third-party services**: implement timeout handling (never await an external call without a timeout bound — use a 5000ms default for HTTP calls, 30000ms for file uploads/downloads) and surface errors to the caller — do not swallow failures silently. When multiple independent async operations can run concurrently (e.g., fetching user profile AND permissions AND settings in the same handler), use `Promise.all([op1, op2, op3])` rather than sequential `await` calls — sequential awaits multiply latency needlessly; use `Promise.allSettled` when partial failure is acceptable and each result must be inspected individually. Ensure all async functions have explicit error handling — no `async` function should allow unhandled Promise rejections to bubble uncaught to the runtime (use `try/catch` or `.catch()`). Never suppress `async` errors silently.
- **If the story adds or changes API routes, RPC procedures, or webhooks**: add **API contract checks** that verify expected status codes (including 404 for missing resources, 400 for validation errors, 401/403 for auth failures), response body shape, error body shape, and authorization behavior. Verify the response includes the correct `Content-Type` header (`application/json` for JSON APIs; do not let a framework silently return `text/html` on error paths). For browser-facing APIs, set appropriate CORS (`Access-Control-Allow-Origin`) headers — never use wildcard `*` for authenticated endpoints. If the story introduces new public-facing pages or API routes, verify the project-level security headers are in place (e.g., `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Strict-Transport-Security`) — in Next.js these go in `next.config.js` `headers()`; in Express/Hono use the existing `helmet` middleware or equivalent; do not add them if the project already sets them globally. If the route is publicly accessible or accepts unauthenticated requests, consider whether **rate limiting** or throttling is needed — if the project already has a rate-limiting middleware or library (e.g., `next-rate-limit`, `express-rate-limit`, `upstash/ratelimit`), apply it to the new route; document the absence of rate limiting in `diff_summary` if not applied so the evaluator can assess the risk. Prefer existing request helpers and mock external dependencies.
- **If the story accepts user input**: use parameterized queries only for database writes (never string-concatenate SQL); escape or sanitize output for HTML contexts to prevent XSS; validate and reject unexpected input shapes at the boundary (not deep in business logic). Normalize string inputs before validation and storage: trim leading/trailing whitespace, and lowercase email addresses before storage and comparison — a user registering as `" User@Example.COM "` and later logging in as `user@example.com` must match. If the project already uses a schema-validation library (e.g., Zod, Valibot, Yup, Joi), declare the input schema with that library and use `safeParse` / `parse` at the route or server action boundary — do not write manual `if (!field)` guards that duplicate what the schema expresses. Use `z.infer<typeof mySchema>` (or the equivalent schema-inference utility for the chosen library) to derive TypeScript types directly from the schema — never write a separate interface that duplicates the schema shape, as the two will drift over time. If no library is present, use structured type guards. Return a 400 with a structured error body listing the invalid fields so callers can surface actionable messages. For file upload endpoints, enforce a maximum file size limit and restrict accepted MIME types — reject oversized payloads with a 413 status before processing.
- **If the story introduces WebSocket or real-time connections** (WebSocket, Server-Sent Events, Socket.io, Ably, Pusher): ensure the connection is closed/unsubscribed in a cleanup function (`useEffect` return or component unmount) to prevent connection leaks. Authenticate the connection at the handshake layer — do not assume WS connections inherit HTTP session auth automatically. Test that the client gracefully handles server-side disconnects with reconnection logic, and that messages are validated against an expected schema before processing.
- **If the story introduces a feature flag**: always default to `false` / disabled so the new behavior is opt-in and a deploy without configuration doesn't break production. If the project uses a flag library (e.g., LaunchDarkly, Unleash, OpenFeature, `@vercel/flags`), implement the flag through that library — do not roll a new flag mechanism. If no flag library exists, implement as a plain environment variable boolean (e.g., `process.env.FEATURE_NEW_CHECKOUT === 'true'`) and guard every entry point of the new behavior behind it. Document the flag name, type, default, and the condition that enables it in the `feature_flags` field of `RALPH_READY_FOR_EVAL` and `RALPH_DONE`.

## 5. Environment variables and secrets

- **No hardcoded secrets, API keys, or credentials** — use environment variables. If a secret is required for the feature, reference `process.env.VAR_NAME` and document the variable name, description, and example value in the `summary` field of `RALPH_DONE`. If the story introduces new required environment variables, add a startup validation check (e.g., throw at module load if the variable is missing) so the app fails fast rather than silently at runtime when the variable is absent. Also add the new variable to `.env.example` (with a placeholder value, not the real secret) so teammates know the variable is required — if `.env.example` does not exist, note its absence in `diff_summary` but do not create it without explicit instruction.
- Do NOT create or modify `.env`, `.env.local`, or any dotenv file — environment configuration is outside your scope.
